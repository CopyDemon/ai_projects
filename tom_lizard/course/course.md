# Tom Lizard 课程

一课一个文件，文件名是 `lessonXX_主题.py`。每课都是能单独运行的小程序，学一个概念。学会的东西再搬进 Tom 的正式应用代码里。

有些课是直接在 `app/` 里给 Tom 加功能，这种课没有单独的 lesson 文件，笔记照样写在这里，注明代码在哪。

运行任何一课：

```
conda activate tom_lizard
cd tom_lizard/course
python lessonXX_主题.py
```

## 第一课：agent 循环

学到的概念：

- **LLM**：大语言模型。它只会做一件事，读一段文字，接着往下写。
- **Ollama**：在自己电脑上跑开源模型的软件。它在后台开一个服务，代码通过它和模型说话。
- **tool calling**：给模型一份工具清单，模型可以回答“我要调用某个工具，参数是这些”。模型自己不执行任何东西，执行的是我们的代码。
- **agent 循环**：问模型，模型要工具就执行，把结果发回去，再问，直到模型直接给出回答。agent 的核心就是这个循环。
- **messages**：对话记录。模型本身不记事，每次请求都要把完整记录发过去。
- **thinking**：有些模型回答前会先输出一段思考过程，qwen3 就是。

实际跑的结果：问 (11434 + 12341) * 412，Tom 调用了 add 和 multiply，答案 9795300，正确。跑了两次都对。

注意到的问题：模型在同一轮里同时调用了 add 和 multiply，multiply 用的 23775 是它自己心算的，没等 add 的结果。这次算对了，但说明模型可能自己瞎算，不一定老老实实用工具。

## 第二课：网页界面

代码在 `app/` 里，不是单独的 lesson 文件：

- `app/agent.py` Tom 的大脑，就是第一课的 agent 循环，改成能接收整段对话
- `app/main.py` 后端，用 FastAPI 写的
- `app/static/index.html` 前端，就是浏览器里看到的聊天页面，HTML、CSS、JavaScript 都在这一个文件里

启动方法见 environment.md 的“怎么启动 Tom”。

学到的概念：

- **前端**：跑在浏览器里的部分，负责显示界面、接收你的输入。用 HTML 写结构，CSS 管样式，JavaScript 管动作
- **后端**：跑在电脑上的 Python 程序，负责真正干活，这里就是调用模型
- **服务器和端口**：后端启动后会一直开着等人来连接。端口就像门牌号，Tom 用 8000，Ollama 用 11434
- **HTTP 请求**：前端和后端说话的方式。`GET` 一般是拿东西，比如拿网页；`POST` 一般是送东西过去让它处理，比如送一句话给 Tom
- **API**：后端规定好的接口。`/api/chat` 就是一个 API，说好了送什么格式的数据进来，会返回什么格式的数据
- **JSON**：前后端之间传数据最常用的格式，长得像 Python 的字典
- **FastAPI 和 uvicorn 的分工**：FastAPI 负责定规矩，哪个网址干什么。uvicorn 负责开门迎客，接请求再交给 FastAPI
- **数据校验**：用 pydantic 规定请求必须长什么样。测试时故意发了一个 role 是 hacker 的消息，被直接拒绝，返回 422 错误
- **def 和 async def**：调用 ollama 时程序要卡住等结果。FastAPI 官方文档说，这种会卡住的库要用普通 `def`，FastAPI 会把它放到另一个线程跑，不会卡住整个服务器
- **对话记录存在哪**：存在浏览器的 JavaScript 变量里，每次发消息都把整段记录发给后端。后端什么都不存。好处是简单，坏处是刷新网页记录就没了。以后做记忆功能时再改

为什么选 FastAPI 不选 Gradio 或 Streamlit：2026-10-02 在 PyPI 查过，Gradio 6.29.1 直接依赖 30 多个包，包括 pandas、numpy、huggingface-hub；Streamlit 1.65.0 也要 pandas、pyarrow 等一大堆。FastAPI 加 uvicorn 只多装了 6 个包。而且前后端分开写，以后做正式应用、做手机端、给别人接活，都是这套结构。

实际跑的结果：

- 用 curl 测了后端：网页和头像能打开，格式不对的请求返回 422，多轮对话能记住名字和上一轮的结果
- 用无头 Chrome 模拟真人操作：打字、发送、等待时发送按钮变灰、显示回答、显示思考过程，都正常
- 用 environment.yml 重建了一个干净环境，网页照样能用

发现的问题：

1. **模型心算出错，这次真的发生了。** 问 (11434 + 12341) * 412，Tom 同时调用了 add 和 multiply，multiply 用的是它自己心算的 33775，正确的是 23775，于是工具算出了错误的 13915300。好在 Tom 看到结果后自己起了疑心，重新算了一遍，最后答对了。网页里把工具调用显示出来，才让我们看见了这个问题。还没修
2. **偶尔用英文回答中文问题。** 第一次测试时出现过。改了 system prompt，说得更明确，之后测的几次都是中文。但模型输出本来就有随机性，qwen3:8b 默认 temperature 是 0.6，不能保证以后不出现
3. **要等完整个回答才显示。** Tom 思考时间长的时候要干等十几秒。以后可以做成一个字一个字流出来

## 问答：能不能在现成的模型上加东西或删东西

2026-10-02 问的。答案是能，从简单到难分五层：

1. **提示词**：system prompt，不动模型。Tom 在用
2. **Modelfile**：把提示词和参数打包成新名字的模型，不动模型，外面包一层。实际测过，原版说自己是 Qwen，包了一层后说自己是 Tom
3. **外面加系统**：工具、记忆、查资料，不动模型。路线图后面几步就是这个
4. **微调**：用自己的数据训练，真正改模型。Mac 上能训练，能不能装回 Ollama 还没确认
5. **从头训练**：这台电脑做不了

学到的道理：大部分时候不用改模型本身，在模型外面下功夫更划算。微调适合教说话风格和固定格式，不适合教新知识。

## 第三课：从零训练一个 1KB 的小 Tom

问题是这样提的：假设 Tom 是一个什么都不会的模型，只有 1KB 大，怎么用算法一点点教会它认识 1 2 3 4 5。

代码 `lesson03_tiny_tom.py`，跑一次不到 1 秒。每次运行会生成 `tiny_tom_brain.bin`，就是训练好的小 Tom 的大脑。

### 做法，一共七步

1. **准备教材**：每个数字画在 5 列 7 行的格子里，一共 35 个点，黑是 1 白是 0。再随机把 10% 的点黑白反过来，模拟写歪的字。每个数字做 200 份当课本，另外做 100 份当考卷，考卷 Tom 学的时候没见过
2. **造一个空白大脑**：35 个输入点 → 6 个中间神经元 → 5 个输出，分别代表 1 到 5。一共 251 个参数，全是随机数
3. **训练前考一次**：正确率 36%。五选一瞎猜是 20%，这次随机出来的大脑碰巧好一点，换个随机种子就不一样
4. **训练**：反复做四件事
   - 猜：看 50 张图，给出答案
   - 对答案：算出离正确答案差多少，叫 loss
   - 找方向：算出每个参数往哪边调能让 loss 变小，叫反向传播
   - 调一点点：每个参数朝那个方向挪一小步，步子大小叫学习率，这里是 0.5
5. **训练后再考**
6. **考一个没学过的 6**
7. **存大脑**：把 251 个参数存成文件，正好 1004 字节

### 实际跑的结果

| 时间点 | loss | 考试正确率 |
| --- | --- | --- |
| 训练前 | | 36% |
| 调整 1 次后 | 1.394 | 57.0% |
| 调整 3 次后 | 1.114 | 82.4% |
| 调整 4 次后 | 0.849 | 62.6%，倒退了 |
| 调整 6 次后 | 0.829 | 94.8% |
| 调整 20 次后，学完一轮 | 0.077 | 99.6% |
| 调整 200 次后，学完十轮 | 0.002 | 99.8% |

同一个带噪点的 3，训练前 Tom 说是 2，只有 4% 觉得是 3。训练后 100% 确定是 3。

不同噪点的考卷：

| 噪点 | 正确率 |
| --- | --- |
| 0% | 100% |
| 10%，跟课本一样 | 100% |
| 20% | 96.2% |
| 30% | 78.5% |

给它看从来没学过的 6，它 **100% 确定是 3**。

### 学到的概念

- **模型就是一堆数字**：小 Tom 是 251 个数字，qwen3 也是一堆数字，只是多得多。“学会”就是把这些数字调到合适的值
- **训练就是猜、对答案、找方向、调一点点，重复很多次**。所有神经网络，包括大语言模型，都是这个套路
- **loss**：衡量错得有多离谱的一个数字。训练的目标就是让它变小
- **反向传播**：从错误倒推回去，算出每个参数该往哪边调、调多少
- **学习率**：每次调多大一步。太大会来回乱跳，太小学得太慢
- **batch**：一次看一小批再调，不是一张一张调，也不是全看完才调
- **轮，也叫 epoch**：把整本课本看完一遍
- **训练集和测试集要分开**：拿学过的题考没意义，要用没见过的题考才知道是真学会还是死记硬背
- **正确率会倒退**：第 4 次调整后从 82% 掉到 62%。因为每次只看 50 张图，这 50 张让参数往某个方向调，对别的图可能变差。多调几次就整体变好了
- **模型只会它学过的东西**：没教过 6，它不会说“我不认识”，而是硬选一个最像的，还 100% 确定。大模型胡说八道也有这个原因
- **难度超出课本就会变差**：课本只有 10% 噪点，考 30% 噪点就掉到 78%
- **随机种子**：程序开头固定了随机数，所以每次运行结果都一样，方便对比

### 跟 Tom 的关系

我们在网页里用的 qwen3:8b 也是这么训练出来的，只是教材是海量的文字，任务是猜下一个字，参数多到要用很多显卡训练很久。原理一样。

## 问答：模型运行时是整个塞进内存的吗

2026-10-09 问的，在这台 MacBook 上实测。

**答案：是的，整个模型都会放进内存，而且还要再加一块存上下文。**

qwen3:8b 的权重文件在硬盘上是 5.23GB。用不同的上下文长度加载，`ollama ps` 看到的实际占用：

| 上下文长度 num_ctx | 实际占内存 | 比文件多出来 |
| --- | --- | --- |
| 4096 | 5.92GB | 0.69GB |
| 16384 | 7.85GB | 2.62GB |
| 32768，0.40.0 不指定时的默认值 | 10GB | 约 4.8GB |
| 40960，qwen3:8b 的上限 | 11.51GB | 6.28GB |

三次都是 100% GPU，就是全部放在 GPU 能用的内存里。

### 为什么要全部放进去

- 模型每生成一个 token，都要用到全部参数算一遍。如果有一部分在硬盘上，每个字都要去硬盘读，慢得没法用
- 所以前面说吐字速度看内存带宽：每生成一个字，就要把这 5GB 左右的参数从内存里读一遍
- 例外是 MoE 模型，就是“混合专家”模型。它也要全部放进内存，但每个字只用其中一部分专家，所以读得少、跑得快。比如之前在 Ollama 列表里看到的 nemotron-3.5-lightning，总共 30B，每次只用 3B

### 多出来的那块是什么

- 叫 **KV cache**。模型读过的每个 token，都要留一份中间计算结果，后面生成新字时要回头看
- 上下文越长，存的越多。实测下来大约每 1000 个 token 多占 0.15GB，基本是直线增长
- Ollama 官方文档说可以用 `OLLAMA_KV_CACHE_TYPE` 把它压缩：默认 f16，`q8_0` 大约省一半，`q4_0` 大约省到四分之一，精度会损失一点。没实测过

### 其他实测到的

- **官方文档和实际不一样**：文档写默认上下文是 4096，但 Ollama 0.40.0 不指定时实际用了 32768。以实测为准，文档可能没更新，或者默认值是按机器内存自动定的，这个没查到
- **模型用完不会马上释放**：默认在内存里留 5 分钟，`ollama ps` 的 UNTIL 那一列就是什么时候释放。想马上释放用 `ollama stop 模型名`
- **qwen3:8b 在 0.40.0 上还是用 llama.cpp 跑**，`ollama ps` 的 RUNNER 那一列是 llamacpp，不是 MLX。0.40.0 的发布说明说 MLX 支持的模型才会自动用 MLX，这个模型显然不在其中，或者要下专门的 MLX 版本

### 这对 Tom 意味着什么

- Tom 网页没有指定上下文长度，所以现在每次加载占 10GB 左右
- qwen3 的思考过程很长，会吃掉很多上下文。聊得很长以后，超出上下文长度的部分会被丢掉或者出错，这个还没测过
- 选电脑时不能只看模型文件大小，要再加上上下文要用的内存
